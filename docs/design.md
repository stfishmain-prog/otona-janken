# 大人は目的無くジャンケンをしない。 設計書

Oct 14, 2026 · @サトシ

## 1. 概要

スプレッドシート「大人は目的無くジャンケンをしない。」を、ログイン不要・ブラウザだけで使える静的Webアプリにする。サーバーとデータベースを持たないため、月額0円で半永久的に公開できる。

- **目的**: ゲーム（ジャンケン等）の敗数を記録し、BET POINTに基づく各PLAYERの清算POINTを自動計算する。ゲーム性は持たず、集計に徹する。
- **追加機能**: 清算ボタンで「誰が誰に何POINT渡すか」を最少に近い受け渡し回数で表示する（Walicaの精算画面に相当）。清算後もゲーム画面へ戻って続行できる。
- **利用シーン（想定）**: 飲み会や旅行で、1台のスマホを囲んで記録する。入力データは端末のブラウザ内にだけ保存し、サーバーへ送信しない。
- **言語**: 日本語で初版を作り、翻訳ファイルの追加だけで他言語に広げられる構造にする。
- **アプリ名**: 大人は目的無くジャンケンをしない。（多言語版では言語ごとに翻訳する。8章）

## 2. 現行スプレッドシートの分析

入力は3項目（PLAYER・BET POINT・敗数）だけで、残り3項目は計算で求まる。サンプル（6人・BET 500・敗数1〜6）を下記の式で再計算すると、清算POINTはシートと完全に一致した（1,500 / 900 / 300 / −300 / −900 / −1,500、合計0）。

| 項目 | 種別 | 内容 |
| --- | --- | --- |
| PLAYER | 手入力 | ゲーム開始前に名前を入力 |
| BET POINT | 手入力 | ゲーム開始前にPLAYERごとに設定（Web版は初期値100） |
| 敗数 | 手入力 | 各PLAYERが負けた回数 |
| 加点POINT | 自動計算 | 他PLAYERそれぞれの「BET × 敗数 ÷（人数 − 1）」の合計（端数切り捨て） |
| 減点POINT | 自動計算 | BET × 敗数 × −1 |
| 端数POINT | 自動計算 | Web版で追加。割り切れず配らなかった余りを、負けたPLAYER自身が保持 |
| 清算POINT | 自動計算 | 加点 + 減点 + 端数。全員の合計は必ず0 |

シートに定義がなく、Web化で決める必要がある点は次の4つ。本書では仮の方針を置き、要確認とする。

- **端数処理**: 割り切れない場合の扱い（例: 7人でBET 500 → 1人あたり83.33…）。→ 端数は配らず、負けたPLAYER自身の端数POINT欄に残す（7章）。
- **BETの個別設定**: シートは個別設定可。→ 初期値100を全員に入れておき、一括変更・個別変更ができるようにする。
- **途中参加・離脱**: 人数が変わると分配の分母が変わる。→ 初版はゲーム中の人数固定。人数を変えると全敗数を新しい人数で再計算する旨を警告する。
- **敗数の修正**: シートは数値を直接書き換えられる。→ ＋/−ボタンと「元に戻す」で修正する。

## 4. 技術構成とアーキテクチャ

Vite + React + TypeScript の静的SPAを作り、GitHubへのpushで自動デプロイする。サーバー・DB・外部APIは使わず、状態は利用者のブラウザ（localStorage）に保存する。

開発PCからpushするだけで公開まで自動で流れ、利用者の端末ではデータが外へ出ない。

| 層 | 採用 | 理由 |
| --- | --- | --- |
| 言語・UI | TypeScript + React | Claude Codeが最も安定して書ける組み合わせ。型で計算ミスを防ぐ |
| ビルド | Vite | 設定がほぼ不要。出力は静的ファイル（dist/）だけ |
| スタイル | 素のCSS 1ファイル（CSS変数） | 依存ゼロ。生成コードが短くトークンを節約できる |
| 状態管理 | useReducer + localStorage | ライブラリ不要 |
| 画面切替 | ルーターなし（state で3画面を切替） | 画面が3つだけのため |
| 多言語 | 自前の t() 関数 + JSON辞書 | 依存ゼロ（8章） |
| テスト | Vitest（計算ロジックのみ） | Viteと設定を共有できる |
| ホスティング | Cloudflare Workers（静的アセット配信） | 無料で商用利用可。広告導入時も移行不要 |

```json
{
  "name": "otona-janken",
  "compatibility_date": "2026-10-14",
  "assets": { "directory": "./dist" }
}
```

**独自ドメイン**: 公開時点で **otona-janken.com** を取得する（決定）。アプリ名のローマ字なので覚えやすく、言語を問わずブランド名として通用する。Cloudflare Registrarで取得すれば登録・更新とも卸値で、DNS設定も同じ画面で済む（[Cloudflare Registrar](https://domains.cloudflare.com/ja-jp)）。空き状況は取得時に確認する。

| 候補 | 評価 |

「ゲームに戻る」と「SET UPに戻る」は敗数を保持し、敗数が消えるのは「NEW GAME」だけ。

### UIの決めごと

- 「負け ＋1」は誤タップしても「元に戻す」で即座に取り消せる。確認ダイアログは出さない（連打の妨げになるため）。
- 清算POINTは正を青、負を赤で表示し、色だけに頼らず「+」「−」の符号も付ける。
- 「NEW GAME」「PLAYER削除」など取り消せない操作だけ確認ダイアログを出す。
- 広告枠は「負け ＋1」ボタンから離れた位置（フッター・S3下部）にだけ置く。
- アプリ名はS1だけに表示する（S2・S3では出さない）。スマホ幅では「大人は目的無く」「ジャンケンをしない。」の2行に分けて表示し、2行目は末尾の「。」を除いた部分で中央にそろえる。
- 初めて開いた人が使い方ページを見なくても分かるよう、各画面に短い説明文を置く。説明文は本文より小さく控えめな色（--text-muted）にし、スマホの縦画面を占領しない量にとどめる。詳しい説明は使い方ページに書き、言い回しはアプリ内の説明文とそろえる。
- POINTは金銭ではないため、説明文では「受け渡し」「渡す」など金銭を連想させる言い方を避け、「清算」「清算するPOINT」「POINTの移動」「移す」と書く。他言語でも transfer・give などの送金を思わせる語は使わない。
- 説明文の中のボタン名は、ボタンと同じ訳語のキー（例: game.settle）を埋め込み、言語ごとのずれを防ぐ。

## 6. データモデル

保存するのは「PLAYER一覧」と「負けたPLAYERの履歴」だけで、敗数・加点・減点・清算POINTはすべて毎回計算で求める。履歴を唯一の正とすることで、「元に戻す」は履歴の末尾を1件消すだけになり、集計のずれが起きない。

```typescript
// src/types.ts
export const DEFAULT_BET = 100;      // 新規PLAYERのBET初期値
export const MAX_PLAYERS = 20;

export type Player = {
  id: string;      // crypto.randomUUID()
  name: string;
  bet: number;     // 0以上の整数（初期値 DEFAULT_BET）
};

export type GameState = {
  version: 1;                         // 保存形式のバージョン（将来の移行用）
  players: Player[];                  // 表示順 = 配列順
  history: string[];                  // 負けたPLAYERのidを1ゲーム1件で追記
  view: 'setup' | 'game' | 'settle';  // 現在の画面
  updatedAt: number;                  // Date.now()
};

// 以下は保存しない（計算結果）
export type PlayerResult = {
  id: string; name: string; bet: number;
  losses: number;    // history 内の出現回数
  gain: number;      // 加点POINT
  loss: number;      // 減点POINT（0以下）
  fraction: number;  // 端数POINT（配らなかった余り。0以上）
  net: number;       // 清算POINT = gain + loss + fraction
};

export type Transfer = { from: string; to: string; amount: number };
```

| 項目 | 仕様 |
| --- | --- |
| 保存先 | localStorage、キー `otona-janken:state:v1` |
| 保存タイミング | state が変わるたびに即時保存 |
| 読込失敗時 | 壊れたデータ・バージョン不一致は初期状態で起動し、エラーを出さない |
| 初期状態 | PLAYER 2人（BETは各100）、history は空、view は setup |
| PLAYER追加 | BETは DEFAULT\_BET（100）で追加。一括変更した後は、その値で追加 |
| −1ボタン | そのPLAYERのidを history の後ろから探して1件削除 |
| PLAYER削除 | そのPLAYERのidを history からも全削除（確認ダイアログあり） |
| 言語設定 | 別キー `otona-janken:lang` に保存 |

## 7. 計算ロジックと清算アルゴリズム

計算はすべて整数で行う。割り切れない端数は誰にも配らず、負けたPLAYER自身の「端数POINT」欄に残すため、全員の清算POINT合計は常に0になる。清算は貪欲法で行い、受け渡し回数は最大でも「人数 − 1」回に収まる。

### 集計式（src/logic/calc.ts）

b = BET POINT、k = 敗数、n = 人数として、PLAYER i について次のとおり。

```latex
L_i = -\,b_i k_i \quad G_i = \sum_{j \ne i} \left\lfloor \frac{b_j k_j}{n-1} \right\rfloor \quad R_i = b_i k_i \bmod (n-1) \quad N_i = G_i + L_i + R_i
```

L が減点POINT、G が加点POINT、R が端数POINT、N が清算POINT で、N の全員分の合計は必ず0。シートのサンプル（6人・BET 500・敗数1〜6）は割り切れるので R はすべて0となり、シートと同じ値になることを確認済み。

### 端数処理

負けたPLAYER j の分配総額 D = b\_j × k\_j を、次の手順で扱う。減点POINTはシートどおり BET × 敗数 のまま変えず、配らなかった分は端数POINTとして別欄で見せる。

1. j 以外の n − 1 人に、floor(D ÷ (n − 1)) ずつ加点する。
2. 余り D mod (n − 1)（0〜n − 2）は誰にも配らず、j 自身の端数POINTとする。
3. 余りはPLAYERごとの敗数合計でまとめて計算する（1ゲームごとに切り捨てない）。BETや人数を変えたら全履歴から計算し直す。

例: 7人・BET 500で1敗 → D = 500。他の6人に83ずつ（計498）を加点し、負けたPLAYERは減点 −500・端数 +2・清算 −498。全員の合計は0。

### 清算アルゴリズム（src/logic/settle.ts）

1. 清算POINTが正の人を受取側、負の人を支払側（絶対値）に分ける。0の人は除外する。
2. 金額が完全に一致する支払側と受取側のペアを先に1回で清算する（回数を減らすため）。
3. 残りを金額の大きい順に並べ、最大の支払側から最大の受取側へ min(両者) を渡す。0になった側を外し、全員0になるまで繰り返す。
4. 結果は支払側の表示順で並べる。

厳密な最少回数を求める問題は人数に対して計算量が爆発するため、初版は上記で十分とする。20人以下なら一瞬で終わる。

### テストケース（Vitest）

| ケース | 入力 | 期待結果 |
| --- | --- | --- |
| シートの再現 | 6人・BET 500・敗数1〜6 | 清算 1,500 / 900 / 300 / −300 / −900 / −1,500、端数はすべて0。受け渡し3回（⑥→①1,500、⑤→②900、④→③300） |
| 端数 | 7人・BET 500・1人だけ1敗 | 他6人の加点83ずつ。敗者は減点 −500・端数 +2・清算 −498。合計0 |
| 端数はまとめて計算 | 7人・BET 500・同じ1人が3敗 | D = 1,500 なので他6人に250ずつ、端数0（1ゲームごとの切り捨てなら249ずつ・端数6になるが、そうしない） |
| BETが異なる | 3人・BET 100/200/300・敗数1/1/0 | 清算 0 / −150 / 150。受け渡し1回 |
| 全員0敗 | 初期状態（2人・BET 100） | 全員0、受け渡し0回 |
| 2人 | BET 100・敗数3/1 | 清算 −200 / 200。受け渡し1回 |
| 不変条件 | ランダム入力100通り | 清算合計0、0 ≤ 端数 < n − 1、受け渡し回数 ≤ n − 1、受け渡し後に全員0 |

## 8. 多言語対応設計

初版から画面の文言をすべて翻訳辞書経由にしておき、言語の追加は「JSONファイル1つ追加＋登録1行」で済む形にする。日本語版だけの段階でもこの構造で作るのが、後から作り直さないための唯一の条件。

| 項目 | 方針 |
| --- | --- |
| 辞書 | `src/i18n/ja.json` を正とし、`en.json` などを同じキーで追加。キーは `game.addLoss` のような「画面.用途」形式 |
| 呼び出し | 自前の `t('key', {name})` 関数と `useT()` フック。変数は `{name}` 形式で埋め込む |
| 欠けた訳 | 該当言語にキーがなければ英語 → 日本語の順でフォールバック |
| 言語の決定 | 保存済み設定 → ブラウザの言語（navigator.language）→ 日本語 |
| 数値 | `Intl.NumberFormat(locale)` で桁区切り（1,500 / 1.500 など国ごとに変わる） |
| 用語 | アプリ名・「POINT」・「BET」も辞書に入れ、言語ごとに訳す（英語名は「Grown-ups Don't Play JANKEN for Nothing.」。JANKENを知らない人向けに、説明文とOGPに「JANKEN = Rock-Paper-Scissors」と添える） |
| 既定名 | 空欄時の「PLAYER 1」も辞書から生成 |
| レイアウト | 右から左へ書く言語（アラビア語等）に備え、CSSは `margin-inline-start` など論理プロパティで書く |
| HTML | 言語切替時に `<html lang>` とページタイトルを更新 |

**翻訳の作り方**: 辞書は数十キー程度の小さなJSONなので、言語追加はClaude Codeに「ja.json を〇〇語に翻訳して xx.json を作成」と頼むだけで済み、トークン消費も少ない。公開後、ネイティブ話者に一度確認してもらうのが望ましい。

**検索流入を増やしたい場合（後続検討）**: 言語ごとにURLを分ける（`/en/` など）と各国の検索結果に出やすくなる。初版はURL 1つで、必要になった時点でビルド時に言語別HTMLを出力する方式を検討する。

## 9. 広告導入の設計方針

広告は付けられる。前提4つのうち「ホスティング」と「独自ドメイン」は初版の公開時に満たすので、広告導入時に残るのは「同意管理とプライバシーポリシー」と「審査に通る中身」の2つ。初版は広告コードを入れず、差し込み口（AdSlot）だけを用意しておく。

| 条件 | 内容 | 本アプリでの対応 |
| --- | --- | --- |
| ホスティング | Vercel Hobbyは非商用限定で、AdSense等の広告掲載は商用扱い（[Vercel](https://vercel.com/docs/limits/fair-use-guidelines)） | 初版からCloudflareで公開するので対応済み（4章） |
| 独自ドメイン | AdSenseはトップレベルドメインで審査し、2023年3月以降はサブドメイン単独の追加ができない（[解説記事](https://www.webnots.com/how-to-add-subdomains-in-google-adsense-account/)） | 公開時に otona-janken.com を取得するので対応済み。これが唯一の固定費 |
| 同意管理 | EEA・英国・スイスの利用者にパーソナライズ広告を出すには、Google認定のTCF対応CMPが必要（[Google](https://support.google.com/adsense/answer/13554116)） | AdSense管理画面の同意メッセージ機能で対応できる見込み。申請時に要確認 |
| プライバシーポリシー | 広告Cookieの利用と第三者配信を明記する | `public/privacy.html` を言語ごとに用意 |
| サイトの中身 | 道具だけの1ページは「有用性の低いコンテンツ」として不承認になることがある | 使い方・ルール説明・FAQのページを追加してから申請。POINTは得点の集計用で金銭を賭けるものではない、と明記する |
| 配置 | 誤クリックを誘う配置はポリシー違反 | 「負け ＋1」から離し、フッターとS3下部だけに置く |

**実装方針**: 広告は `src/components/AdSlot.tsx` 1か所に閉じ込める。環境変数 `VITE_ADS_ENABLED=true` の本番ビルドでだけ広告スクリプトを読み込み、それ以外は何も描画しない。広告を出すときは枠の高さを固定で確保し、表示時に画面がずれないようにする。

## 10. ディレクトリ構成・テスト・デプロイ・運用

計算ロジック（logic/）と画面（components/）を分け、テストはロジックだけに書く。デプロイはGitHubのmainブランチへのpushだけで完了し、公開後の定常作業はない。

```text
/
├─ CLAUDE.md            Claude Code 用の開発ルール（短く保つ）
├─ docs/design.md       本設計書（Markdownで書き出して配置）
├─ wrangler.jsonc       Cloudflare の設定（4章、数行のみ）
├─ index.html
├─ public/              favicon、privacy.html（広告導入時）
├─ src/
│  ├─ main.tsx
│  ├─ App.tsx           画面の切替のみ
│  ├─ types.ts          6章の型定義と定数
│  ├─ logic/
│  │  ├─ calc.ts        集計・端数処理（純粋関数）
│  │  ├─ settle.ts      清算アルゴリズム（純粋関数）
│  │  └─ *.test.ts      7章のテストケース
│  ├─ state/store.ts    useReducer + localStorage 保存・復元
│  ├─ i18n/             index.ts（t関数）、ja.json、en.json …
│  ├─ components/       Setup.tsx、Game.tsx、Settle.tsx、AdSlot.tsx
│  └─ styles.css
└─ package.json
```

| 項目 | 方針 |
| --- | --- |
| テスト | `npm test`（Vitest）で7章のケースを実行。画面のテストは書かず、手動確認で済ませる |
| 型・品質 | `npm run build` が型チェックを兼ねる。push前に test と build が通ることを確認 |
| デプロイ | GitHubリポジトリをCloudflare（Workers & Pages）に接続。ビルドコマンド `npm run build`、デプロイコマンド `npx wrangler deploy`。mainへのpushで本番に反映 |
| ドメイン | Cloudflare Registrarで取得し、同じダッシュボードでWorkerに割り当てる |
| 継続性 | 外部サービス依存がないため、放置しても動き続ける。`dist/` は他のどの静的ホスティングにも置ける |
| 依存更新 | 必須ではない。年1回程度 `npm outdated` を見て、セキュリティ修正のみ反映 |

## 11. 開発フェーズと要確認事項

フェーズ0〜3で日本語版を公開し、4で多言語、5で広告を入れる。各フェーズは完了条件を満たしてから次へ進む。

1. **フェーズ0 準備**: GitHubリポジトリ作成、Vite初期化、CLAUDE.md と docs/design.md を配置。完了条件: `npm run dev` で初期画面が表示される。
2. **フェーズ1 計算ロジック**: types.ts、calc.ts、settle.ts とテスト。完了条件: 7章のテストがすべて通る。
3. **フェーズ2 画面**: S1〜S3、自動保存、日本語辞書。完了条件: スマホで一通り操作でき、再読み込みしても状態が戻る。
